# 首次特效卡顿采集

开发者菜单中搜索 `卡顿诊断`，所有入口位于 `RimUnity` 分类。适用于首次生成某个粒子特效时的瞬时卡顿，也可以在主菜单采集。

## 复现一次并导出

1. 如果要测冷启动，先重启游戏。已经加载过的资源不会因开始采集而变冷；工具不会清空游戏的 Shader/纹理缓存。
2. 关闭其他持续采样的诊断窗口，进入准备触发特效的场景。
3. 点击 **卡顿诊断 1 · 开始采集（60秒）**。复杂复现场景可用 120 秒入口。
4. 关闭开发菜单，空等两三秒取得空闲基线。
5. 触发特效一次；等它稳定后，再触发同一特效一次。尽量保持相同视角、位置和游戏速度。
6. 点击 **卡顿诊断 3 · 停止并导出**。不手动停止也会到时自动保存。

可选用 **卡顿诊断 2 · 添加触发标记** 区分几次操作。标记写入后再关闭菜单并触发特效；菜单本身会影响帧间隔。

完成后会在游戏配置目录的 `RimUnityReports` 子目录生成四个同名前缀的文件，并复制文本报告路径到剪贴板：

- `.txt`：可直接阅读。含测量边界、最慢帧、重叠事件、首次与后续调用、探针覆盖和前后资源状态。
- `.json`：完整的已保留事件、全部聚合统计、帧样本、上下文与探针覆盖。
- `.events.csv`：可按时间、线程、资源或父调用 ID 筛选的事件。
- `.frames.csv`：所有已保留的主循环帧间隔、分配增量、GC 次数和粒子数量。

“再次导出上次报告”用于重新保存内存中的最后一份采集，包括导出失败后的重试；开始新采集会替换它。关闭开发者模式、切换游戏会话或关闭图形设备也会结束采集。报告不会写入存档。

## 采集覆盖

- 清单查找、资源缓存命中/未命中、JSON 文件打开与反序列化、资源载荷加载、模板构建、实例对象图构建与字段绑定。
- 自定义 Shader 加载、标准粒子变体、Linear/HDR 变体、宿主编译和编译缓存标记、磁盘 Shader 缓存读取、Shader Module 获取。
- 纹理加载、缓存读取/图片解码、首次驻留、像素上传、设备纹理分配、上传提交、纹理驻留腾挪。
- 脚本生命周期队列、回调、首次绑定生命周期委托、脚本异常。
- 粒子播放、重置、整组模拟、预热、物理扫描、粒子和拖尾绘制、网格提交、宿主网格上传。
- 宿主图形管线获取、主线程整帧事件、渲染线程整帧事件，以及桥接 Bloom/HDR 阶段。
- 帧间隔、当前线程托管分配、进程分配增量、进程 GC 次数；资源缓存和活动粒子配置的采集前后快照。

本机宿主有几个方法包含当前 Harmony 无法安全改写的只读引用调用。工具使用宿主帧事件和自有方法的直接计时代替改写 `FrameRenderer.CaptureFrame/RecordFrame`、`CompositePass.Record`、`GpuTextureService.CreateTexture2D`。这些覆盖差异会列入报告，不会静默当作零耗时。

## 怎么读报告

先看“采集完整性”和“探针覆盖”，再看“最慢帧间隔及重叠事件”。`OK` 表示探针安装成功，不代表目标调用一定经过该入口。

`Asset.Get` 的 `cache=miss` 表示资源模板缓存未命中；`cache=hit` 表示资源对象已经存在。`Shader.Compile` 的 `compilerCacheHit=True` 是宿主返回的缓存标记；False 也可能来自宿主覆盖文件分支，需结合 `Shader.CompileMiss` 是否出现判断是否实际编译。`Texture.ReadDecode` 的 `textureCacheHit` 是宿主纹理缓存标记。`Texture.FileResident` 会记录调用前是否已有设备资源和 CPU 像素。

`Prefab.Build | instance` 是实例对象图构建，Awake/OnEnable 还可能在外层实例化事务结束后发生，单列为 `Lifecycle.Drain/Callback`。按时间线一起检查，不能把对象图构建时间当作整个 Instantiate 的时间。

粒子组事件会记录待预热根数量、模拟时间跨度及粒子数，实例事件会记录容量、上限、duration、speed、碰撞、拖尾等配置。组内计数扫描最多 512 个系统；上下文最多列出 256 个活动系统。

`First/Second/Third` 始终是**本次采集最早观察到的调用**，不自动等于进程冷启动。`duration` 是包含子调用的 CPU 墙钟时间，`self` 扣除同线程、同会话内已测量子调用。嵌套 duration 不能相加，跨线程的耗时也不能相加当作帧时长。宿主帧事件是独立的外层时间段，不参与嵌套扣除；停止时的 partial main frame 只是部分帧。

所有 `GPU.*`、渲染帧和 Bloom/HDR 计时都是 **CPU 端调用耗时**。工具没有插入 GPU timestamp、像素读回或设备空闲等待，不能用它直接声称 GPU 执行耗时或精确呈现延迟。帧号是最近观察到的主线程桥接帧号；关联渲染线程时优先使用相对毫秒时间。

## 开销与限制

动态探针只在显式采集期间安装，停止时移除；自有 JSON 和渲染阶段的直接探针在未采集时只检查一个空会话引用，不分配对象。安装探针和读取上下文不计入采集时间，但安装过程与 JIT 仍可能影响冷启动条件。采集期间的反射、参数装箱、字符串、锁和记录分配会增加开销，因此本工具用于定位明显 spike，不用于证明微秒级性能改善。

每个 `stage + detail` 聚合全部已完成调用；事件保留最早三次、至少 2ms 的慢调用和异常。最多 4096 个聚合组、25000 条事件、12000 个帧样本。达到上限会显式报告丢弃数量；普通未保留调用仍进入聚合统计。父事件可能没有被保留。停止时还在运行的调用不补算为完整调用，报告列出未完成数量。

采集期间不写磁盘，停止后才导出。采集不会生成特效、清理资源缓存、强制 GC 或修改渲染设置。记录只持有文本和数值，不保留 Map、Pawn、组件或设备资源。用户目录会被替换为 `<USER>`；报告不收集存档内容、Shader 源码或贴图像素。

## 定向验证

`Tools/SpikeCaptureTests` 覆盖嵌套计时、异常、跨线程聚合、截断、会话隔离、快照隔离；可额外指定运行时程序集、游戏目录和 Harmony 路径，验证实际探针安装/移除、实际资源缓存入口和异常透传、out 参数缓存标记及导出结构。

首次使用仍应在游戏内按上述步骤触发两次特效，确认采集到目标资源及实际卡顿。离线测试不代替真实图形设备下的复现。
